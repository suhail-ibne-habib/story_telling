Your instinct is good — you’re basically describing a retrieve-then-rerank pipeline, which is the right shape for this problem. Let me lay it out properly and add the pieces that will actually make the duration/matching problem solvable.
The core problem, restated
You have two representations of the same movie: 1. The recap script — a sequence of events, each with narration text and a target duration (once you synthesize the voice, you know exactly how long each event needs to be). 2. The movie itself — hours of footage with a transcript, shots, and scenes.
The job: for each event, find a contiguous clip of length ≈ the narration duration that visually and semantically matches the event.
Proposed pipeline
Stage 0 — Preprocess the movie once, offline: - Extract the full transcript with timestamps (Whisper with word-level timestamps). - Run shot/scene detection (PySceneDetect or TransNet V2) to get shot boundaries. - Embed every shot’s keyframes with a vision-language model (CLIP / VideoCLIP / SigLIP) and store text-searchable vectors per shot.
Stage 1 — Event → transcript alignment (your idea, refined): Match each recap event to transcript regions. Don’t do raw text overlap — recap narration is paraphrased, not quoted. Instead: - Embed the event text and the transcript in sliding windows (or per subtitle line), then match by semantic similarity. - Use a sequence-alignment pass (like DTW) so events stay in chronological order — event 5 shouldn’t match a scene before event 3. This constraint alone kills most false matches.
This gives you a coarse time window per event. Expect it to be noisy; treat it as a prior, not ground truth.
Stage 2 — Candidate shot retrieval: Within each event’s window (and a bit around it), pull candidate shots. Rank them three ways and fuse the scores: - Visual-text similarity: CLIP score between shot frames and the event description. - Dialogue overlap: does this shot’s dialogue appear in/near the event’s transcript match? - Chronological coherence: prefer shots that keep the edit monotonic in movie time (no jumping backward unless the recap does).
Stage 3 — VLM reranking (your Gemini step — but be smart about it): Send the event description + 3–5 candidate shots (2–3 frames each + their transcript snippets) to Gemini and ask it to pick the best match and explain why. Don’t send 20 shots — VLMs degrade fast with many candidates. Use stage 2 to filter down to a handful. Also ask the VLM to output a per-shot relevance score so you can fall back to the second-best if the clip fails downstream checks.
Stage 4 — Duration fitting (the part people forget): You know the exact audio length per event from TTS. Now fit the clip: - Prefer a shot slightly longer than needed, then trim to audio length. - If the best shot is too short, either allow a cut to an adjacent same-scene shot (cutting on motion or during dialogue is invisible to viewers) or pick the next-best shot that’s long enough. - Avoid ending a clip mid-sentence of dialogue unless the narration is loud there.
Practical advice
Compute embeddings once per movie, cache everything. Stage 0 is expensive; stages 1–3 are cheap and iterative. This lets you tweak the recap without reprocessing.
Add an LLM “event enrichment” step: before matching, expand each recap event with synonyms and likely visual cues (“argument in the rain,” “car chase on the bridge”). Short bare event summaries match poorly; enriched ones match dramatically better.
The transcript is a weak signal for action-heavy scenes. Big action set pieces often have little dialogue. That’s why you need the visual embedding + VLM path as the primary, with transcript alignment as the prior that constrains where to look.
Handle the failure mode explicitly: if every candidate scores below threshold, don’t force a bad clip — insert B-roll (a poster, a title card, or a slow zoom on a related frame). Viewers forgive a B-roll cut; they don’t forgive a mismatched clip.
Validate with humans early: before building all of stage 3, manually check what fraction of events stage 1+2 alone resolves. If it’s already 70–80%, you know the VLM rerank only needs to save the hard 20–30%.

Why AI can’t mark scene changes perfectly
When the AI writes the recap, it only knows the story. It doesn’t know: - How the director actually shot it (maybe the “card reveal” and “casino cheers” are one long continuous camera shot in the movie) - Where the editor actually cut - That the “next day” scene actually starts with a drone shot of the city before showing Jessica
The AI is guessing based on story logic. Sometimes it’ll split where the movie doesn’t cut. Sometimes it’ll merge two things the movie shot in different places.
But here’s the thing — you have TWO sources of scene truth
Source 1: The AI's || markers (guesses, from the story)Source 2: The actual movie's real cuts (PySceneDetect — 100% truth, from the video)
Source 2 never lies. When PySceneDetect cuts the movie, those are the real, physical shot boundaries. That’s ground truth.
So here’s how the pipeline absorbs the AI’s mistakes
Mistake type 1: AI split where the movie doesn’t cut (e.g. AI split “card reveal” and “casino cheers” but it’s one shot)
→ Stage 4 finds the rough area for both takes — and finds they land in the same time window. Stage 5 then offers the same candidate shots for both takes. Gemini might pick overlapping shots, and Stage 7 cuts them differently (different start points within the same long shot).
Result: The video still looks fine — a long take used twice from different angles/timings is a totally normal editing technique.
Mistake type 2: AI merged what the movie split (e.g. one take covers two locations)
→ Stage 4’s rough area will be wide (spanning both locations). Stage 5 finds shots from both. Gemini in Stage 6 picks the best match — maybe only covering part of the take.
Result: Slight mismatch between narration and picture for a few seconds. Not perfect, but watchable.
The trick that fixes most of this 💡
Add a “take sanity check” step between Stage 4 and 5:
If two neighboring takes have OVERLAPPING rough areas → maybe they should be one takeIf one take's rough area is HUGE (3+ minutes) → maybe it should be two takes
This auto-detects both mistake types and can re-split or re-merge takes before you waste Gemini calls.
Bottom line

Can AI mark scene changes perfectly?
❌ No, impossible

❌ No

So don’t chase perfect markers. Chase a pipeline where no single mistake can ruin the final video. That’s what we’ve built. 👍
